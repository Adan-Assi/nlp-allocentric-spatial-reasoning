# Pipeline Fixes — 2026-04-25

A second pass over the labeling pipeline. The previous changes (`CHANGES.md`) corrected the *labeling logic* (3-class semantics, 8-way directions, reachability ordering). This pass fixes the *data plumbing and runtime* — the symbolic oracle was previously labeling every Manhattan row as `Contradictory` because almost no POIs were being recognized as graph nodes, and the iteration loop took ~16 s/row.

## TL;DR

| Symptom | Root cause | Fix |
|---|---|---|
| Terminal flooded with `DEBUG G id in resolve` lines, looked like a crash | Leftover per-POI debug print in `resolve_all_candidates` | Removed the print |
| ~16 s per RVS row, ETA ~37 hours for Manhattan | `hits.iterrows()` over thousands of POI rows × 2–3 calls per RVS row | Vectorized the result construction |
| All 8,103 Manhattan rows labeled `Contradictory` (cands=0 every time) | `_prepare_poi_data` was reading the wrong column for OSM ids; only 1 / 63,000 POIs were being mapped to graph nodes | Switched to the correct column + reverse-index over `G.nodes` for all prefixes |
| 72.5 % of POIs still unmapped after the column fix (ways & relations) | OSM ways/relations have IDs that don't appear as nodes in the street graph at all | Centroid-snap fallback to the nearest graph node, with a 100 m max-distance guard |
| No way to see what the labeler was doing during the run | Only every-50-rows summary in `batch_labeling.py` | Added per-row `tqdm.write` debug line with timing and running tallies |

End result: POI→graph mapping went from **1/63,000 (0.001 %)** to **46,704/63,000 (74.1 %)**, and rows 0–9 now produce the expected mix of Answerable / Ambiguous / Contradictory.

## File-by-file

### `src/oracle_engine.py`

Five changes, all in `OracleEngine.__init__` and `_prepare_poi_data`.

#### 1. Removed leftover debug print

`resolve_all_candidates` had a `print(f"DEBUG G id in resolve: ...")` that fired once per unmapped POI inside the result loop. With ~62,999 unmapped POIs (see below) it flooded stderr/stdout to the point of looking like a crash. The `continue` right after the print already handled the unresolvable POI silently — the print was strictly diagnostic.

#### 2. Vectorized `resolve_all_candidates`'s result construction

Before — Python loop, ~5 k iter/s on pandas:

```python
for _, row in hits.iterrows():
    node_id = row.get('graph_node_id')
    if node_id is None or node_id not in self.G.nodes:
        continue
    results.append({...})
return sorted(results, key=lambda x: x['score'], reverse=True)
```

After — DataFrame-level filtering + numpy column iteration:

```python
hits = hits.dropna(subset=['graph_node_id'])
hits = hits[hits['graph_node_id'].isin(self.graph_node_set)]
hits = hits.sort_values('score', ascending=False)

nids   = hits['graph_node_id'].to_numpy()
scores = hits['score'].to_numpy()
ys     = hits['y'].to_numpy()
xs     = hits['x'].to_numpy()
names  = hits['name'].to_numpy() if 'name' in hits.columns else np.array(['Unknown']*len(hits), dtype=object)

return [{"node_id": n, "name": nm, "score": float(s), "coords": (float(y), float(x))}
        for n, nm, s, y, x in zip(nids, names, scores, ys, xs)]
```

Behaviour audit: same score threshold, same skip-condition, same sort order, same return-dict shape. The only difference is that the per-row attribute lookups happen at the DataFrame level instead of in pure Python.

A new init field `self.graph_node_set = set(self.node_ids)` powers the `.isin()` filter — same big-O as the old `node_id not in G.nodes` check, smaller constant.

#### 3. POI→graph mapping: correct column

The previous `_prepare_poi_data` did:

```python
if 'osmid' in self.poi_df.columns:
    self.poi_df['graph_node_id'] = self.poi_df['osmid'].apply(normalize_node_id)
```

But in this dataset `osmid` holds row-internal indices (`'461'`, `'1084'`, `'1243'`, …) that have nothing to do with OSM. The real OSM node IDs live in the `id` column (`42437096`, `100515086`, …).

Fixed selector:

```python
id_col = 'id' if 'id' in self.poi_df.columns else (
    'osmid' if 'osmid' in self.poi_df.columns else None
)
```

Result on its own: **0 / 2,000 → 1,512 / 2,000 (75.6 %)** match rate on a sample.

#### 4. POI→graph mapping: reverse index for all prefixes

The previous `normalize_node_id` only tried three variants per POI — `f"1#{raw}"`, `f"#{raw}"`, `raw`. But the graph also has nodes prefixed `2#`, `4#`, etc. (e.g. `'4#248827217'`). Those graph nodes were never reachable from POI ids, even when the raw id matched.

New approach — walk `G.nodes()` once, build a reverse index `raw_id → full_node_id`, then look up POI ids in O(1):

```python
def _split(node_id):
    s = str(node_id)
    if '#' not in s: return '', s
    p, r = s.split('#', 1)
    return p, r

def _priority(p):
    if p == '1': return 0   # prefer "1#"
    if p == '':  return 1   # then "#"
    return 2                # then any other ("2#", "4#", ...)

reverse_index = {}
for n in self.G.nodes():
    prefix, raw = _split(n)
    cur = reverse_index.get(raw)
    if cur is None or _priority(prefix) < _priority(_split(cur)[0]):
        reverse_index[raw] = n
```

Tiebreak preserves the prior priority (`1#` > `#` > others) so existing labels stay deterministic.

Combined with #3, this got the direct-match rate to **17,333 / 63,000 (27.5 %)** — but most POIs are ways/relations and still don't have a direct node match in the graph.

#### 5. Centroid-snap fallback for ways & relations

The street graph contains intersections, not building footprints. Most unmapped POIs are *ways* (linear / polygonal features) and *relations* (multi-polygon parks, bus routes, etc.). Their OSM ids will never be in `G.nodes` no matter how cleverly we look them up — but their centroid usually sits within a few metres of a real graph node.

Fallback: vectorized 1-NN KDTree lookup, with a haversine-based distance check so the threshold is in honest metres (KDTree distance is in degree-space and would over-fetch east-west at NYC's latitude):

```python
unmapped_mask = self.poi_df['graph_node_id'].isna() & self.poi_df['x'].notna() & self.poi_df['y'].notna()
coords = self.poi_df.loc[unmapped_mask, ['y', 'x']].to_numpy()
_, idxs = self.node_tree.query(coords, k=1)
snapped = self._node_id_array[idxs]

# Honest metre check
dists_m = utils.haversine_vectorized(coords[:,0], coords[:,1], snapped_lats, snapped_lons)
accepted = dists_m <= 100.0
final = np.where(accepted, snapped, None)
self.poi_df.loc[unmapped_mask, 'graph_node_id'] = final
```

100 m was chosen because Manhattan's grid is ~80 m. Tunable via `SNAP_MAX_M`; for Pittsburgh / Philadelphia 150–200 m is more appropriate.

POIs whose centroid is farther than 100 m are intentionally left unmapped — these are typically polygons covering water or multi-block relations whose "snap target" wouldn't be meaningful for navigation.

This required **reordering `__init__`**: the graph KDTree (`self.node_tree`, `self.node_ids`, `self.graph_node_set`, `self._node_id_array`) is now built **before** `_prepare_poi_data` so the snap step can use it.

#### 6. Init logs visible at startup

So this kind of regression doesn't go undetected next time, the init now prints two lines:

```
DEBUG: POI->graph direct id match via column 'id': 17,333/63,000 (27.5%)
DEBUG: POI->graph snap fallback: 29,371/45,667 unmapped POIs snapped (within 100m). Total mapped: 46,704/63,000 (74.1%)
```

If the first number is < 1 % the column is wrong; if the second is < 50 % the snap radius is too tight.

### `scripts/batch_labeling.py`

Added per-row debug output via `tqdm.write` (so the progress bar stays clean) and a per-row solve timer:

```
[    1/8103] id=1 | Ambiguous     | cands=  33 reach=  33 | cat=CAFE       noun='cafe'                     dir=NE   | stage=strict_category_name_direction       |  0.42s | A=0 Am=1 C=0
```

Fields: row index, sample id, 3-class label, raw vs. reachable candidate counts, extracted (category, noun, direction), resolution stage (which of the three search rounds produced the candidates), per-row solve time, and running tallies of the three labels. The previous every-50-rows summary block is removed.

The exception path now also routes through `tqdm.write` instead of `print`, so failed rows don't break the progress bar.

`import time` added at the top.

## Verification

A 10-row by-hand prediction was made against `extract_rvs_target` + the search-stage logic, then compared to the live labeler output for rows 0–9 of `data/manhattan/manhattan.json`:

| # | Hand-predicted | Live (after fixes) | Notes |
|---|---|---|---|
| 0 | Ambiguous | Ambiguous (37) | "garden" → PARK; multiple parks N/NW/NE within 1500 m |
| 1 | Ambiguous | Ambiguous (33) | "cafe" + NE; many midtown cafés |
| 2 | Ambiguous | Ambiguous (154) | RESTAURANT + NW; West Village density |
| 3 | Ambiguous | Ambiguous (88) | SHOP + SE |
| 4 | Ambiguous | Ambiguous (1169) | RESTAURANT, no direction filter (regex didn't fire) |
| 5 | Ambiguous | Ambiguous (73) | BICYCLE + SE; Citi Bike density |
| 6 | Contradictory | Contradictory | Junk-pattern guard discards "bicycle parking northwest of you" |
| 7 | Answerable / Ambiguous | Answerable (1) | Unique "Subway" name match wins |
| 8 | Ambiguous | Ambiguous (4) | Multiple SE galleries after snap-fallback |
| 9 | Contradictory | Contradictory | Last-anchor regex lands on "the last block" |

10/10 labels are consistent with the by-hand walk-through (Row 7 was a coin-flip in the prediction; the labeler's Answerable is more faithful to the unique-brand name match).

Two known NLP weaknesses surfaced in this small sample and remain *unfixed* on purpose — they belong to a separate work item:

- **Row 6** — the `_JUNK_PATTERNS` guard over-fires on legitimate nouns followed by a directional phrase (`"bicycle parking northwest of you"` is treated as a clause fragment).
- **Row 9** — `_ANCHOR_RE`'s last-`to` strategy can land on a clause fragment (`"the last block"`) when the instruction has multiple `to` clauses.

Both are in `src/extraction_utils.py` and would be a follow-up patch.

## Performance

| Stage | Before | After |
|---|---|---|
| POI→graph mapping rate | 1 / 63,000 (0.001 %) | 46,704 / 63,000 (74.1 %) |
| Per-row solve time (Manhattan) | ~16 s/iter (dominated by `iterrows` over hits) | drops to a few hundred ms once candidates are real (under measurement) |
| Manhattan 8 k rows ETA | ~37 hours | should land in single-digit hours; if still slow, next lever is `joblib.Parallel(n_jobs=...)` over RVS rows in `batch_labeling.py` |

GPU is **not** the right lever for the symbolic labeler — the bottleneck is Python loop overhead on small pandas frames, not compute. GPU/RAPIDS is reserved for Phase 5 LLM inference (`evaluate_llm.py`, `evaluate_llm_masked.py`).
